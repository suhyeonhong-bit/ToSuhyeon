# 온보딩 문서 통합 설계

## 목표

`goal.md`를 프로젝트의 유일한 온보딩 문서로 만든다. 기존 `과제.md`는 별도 교재로 두지 않고, 목적에 종속되는 참고 내용으로 `goal.md`에 통합한 뒤 삭제한다.

## 문서 구조

### 1. 목적과 배경

인턴의 목표와 담당자의 도메인 지식 수준을 투명하게 밝힌다. 철강 지식 자체가 아니라, 어떤 업무에서도 데이터를 근거로 판단하고 실행하는 업무 습관을 만드는 것이 온보딩의 목적임을 정의한다.

### 2. 산업 이해를 위해 정리한 참고 정보

기존 `과제.md`의 내용을 참고 자료로 정리한다.

- 낯선 산업을 분석하는 다섯 가지 질문
- 철강에 적용한 가설과 검증 전제
- 무료·유료 여부와 API 제공 여부를 포함한 데이터 소스 매트릭스
- 이후 확장 가능한 실습 흐름과 데이터 접근 한계

이 섹션의 모든 철강 관련 연결은 정답이 아닌, 데이터로 검증할 가설임을 명시한다.

#### 실무형 데이터 요청 예시

`철강에 적용한 가설` 뒤와 `데이터 소스 매트릭스` 앞에 `실무에서 받을 수 있는 데이터 요청 예시` 소제목을 둔다. 이 항목은 표가 아닌 불릿 목록으로 작성하며, 금리·조선·자동차 전환·지정학·인프라·중국·통상정책·환율·탄소규제와 관련된 열 개의 실무 질문을 담는다. 모든 질문은 결과를 단정하지 않고, 데이터와 가설을 준비해 검토하는 표현을 사용한다.

### 3. 이번 프로젝트의 실제 과제

기존 `goal.md`의 핵심 미션을 한곳에 모은다.

- ECOS와 FRED API 키 발급
- 기준금리·원/달러 환율·미국 철강 PPI(WPU1017) 수집
- 원본(raw)과 가공본 분리 보관
- 월 기준 CSV 통합
- 결측치·시차 처리 근거 기록
- 공식 수치와의 대조 검증

완료 기준과 선택 확장(관세청 HS 72류)을 이 섹션에 함께 둔다.

### 4. 목적 재강조

CLI와 AI를 활용하면 데이터 수집 코드 작성과 반복 실행의 진입장벽은 낮아진다는 점을 강조한다. 다만 API 키 발급, 요청 구조 이해, 원본 보존, 가공 기준 결정, 결과 검증은 본인이 책임져야 한다고 명확히 한다.

## 변경 범위

- `goal.md`를 위 네 섹션으로 전면 재구성한다.
- 문서 첫머리의 `과제.md` 링크를 제거한다.
- `과제.md`를 삭제한다.
- 코드, 데이터, 설정 파일은 추가하거나 변경하지 않는다.

## 검증

- 네 섹션의 제목과 순서가 요청과 일치하는지 확인한다.
- 기존 `과제.md`를 가리키는 링크나 문구가 남지 않았는지 검색한다.
- `goal.md`에서 API 수집·raw 보존·가공·검증 요구사항이 빠지지 않았는지 확인한다.
